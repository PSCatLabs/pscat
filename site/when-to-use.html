When to use pscat

pscat, an image model, or an LLM drawing on its own: which to pick, and where pscat is the wrong tool. This page is the summary; the full argument is the when-to-use guide. What it says about other tools is general and current as of November 2026, and it quotes no benchmarks.

The short answer

  • Use an image model (FLUX, Nano Banana, gpt-image, Midjourney, Stable Diffusion) when the picture is the whole point and nothing in it must be exactly right: a photo-like scene, a face, light and atmosphere, a painterly mood image.
  • Use pscat when something must be exact and checkable: words spelled right, a QR code that scans, numbers that match the data, a layout that prints at size. Or when you need the same result again tomorrow, or with one edit.
  • Use pscat from a text-only model when your assistant cannot make images itself (as of November 2026, Claude reads images but does not generate them): it writes the program, pscat renders it, and the model looks at the render and refines it, with no image-model account, API key or per-image cost.
  • Use an LLM's own SVG, HTML or matplotlib for a quick one-off sketch or diagram.
  • Use both when you want looks and exactness: the image model paints the atmosphere, pscat sets the exact layer on top.

What image models do better

Photorealism, faces and light; rich painterly texture and mood from one sentence; any subject in any style; editing and restyling existing pictures; a first impression in seconds. pscat draws vector paths from a program: it cannot make a photograph, and its painterly look is procedural.

What an image model cannot promise

Image models have become much better at short text, but every character is drawn, not typeset, and nothing checks it. A QR code in a generated image decodes only if every module happens to be right; a generated chart is not computed from your data; margins and sizes are approximate; the output is a raster, not a vector PDF. Open-weights models take a seed, but the same image also needs the same weights, sampler and stack, and the artifact is the image, not source you can diff or hand-edit. Hosted models are usually paid per image or by subscription.

Where pscat wins

  • Text set from real fonts: the standard 35 built in, and 67 catalog faces including Korean, Japanese and Thai.
  • QR codes from a native encoder, drawn as vectors; the PNG, SVG and PDF exports are tested against two independent decoders.
  • Math and charts: pscat chalk for LaTeX, and charts and plots drawn from your numbers.
  • Print-ready vectors: SVG and multi-page PDF, or PNG at 300 dpi that prints at true size.
  • Fixed layout: page templates for cards, letters, certificates, invitations and posters, and a typewriter.
  • Reproducible, editable source: the same program and seed draw the same picture; change one line and only that changes; --sweep-seed and pscat sheet for variations.
  • Local and free per image: one CPU binary, no GPU, no account, MIT or Apache-2.0.

pscat also paints: watercolor, oil, dry brush, chalk, crayon and charcoal (Evening Stream and Alpine Lake are painted with these libraries). It won't out-paint an image model on mood, but its paintings are deterministic under a seed, editable as source, exported as vectors, and composable in one document with exact type, QR codes and charts.

PostScript is a program; SVG and HTML are descriptions

SVG and HTML list what is on the page. PostScript is a programming language, with loops, procedures, recursion, dictionaries and seeded random numbers, so a few lines draw thousands of marks (L-systems, scatter, tilings, fractals, brushes) that SVG would spell out one by one. The libraries are procedures you call. The same program renders to PNG, vector PDF and SVG, so pscat is another route to SVG, not a rival, and multi-page documents and PDF are native. SVG and HTML are the better choice for interactive, animated or reflowing web content, accessibility and editing in the DOM, and they need nothing installed.

Refining by feedback loops

Render, let a critic (you or an art-critic agent) judge the PNG, edit the source, render again, until it looks right: the psart skill is built around this render-look-refine loop, and over MCP the PNG comes straight back to the agent. Each round is a targeted change (a coordinate, a palette entry, a stroke count, an opacity, the seed) with everything else held fixed, so the loop converges; every step is a revertible diff; the final result is reproducible; and --sweep-seed, --sweep and pscat sheet (the review_sheet tool) put candidates side by side. Image models refine too, with conversational edits, inpainting and image-to-image, but as of November 2026 an edit generally re-samples the image: parts you liked can drift, there is no direct numeric control, and the same edit does not repeat. In a hybrid, freeze the image-model layer and iterate on the pscat layer.

A deterministic workflow

With the same pscat version and font packs, the same program and seed give the same pixels on every run, and pscat does its own math, so a seeded render matches on macOS, Linux and in the browser (rarely, a thin curve differs by a pixel or two). The same prompt to an image model gives a different image each time. So a pscat picture behaves like code: reviewable as a diff, testable in CI, cacheable by its source, reproducible later with the same version, and cheap to repeat, since an LLM writes the program once and re-rendering needs no model call. The WebAssembly build renders client-side with no server, GPU or API call: the playground is that build. On main it also writes SVG and PDF; see the next section.

Documents from a web page, the same for every user

A web app can use the WebAssembly build as its document engine: a PostScript template, filled with the user's data, run in the user's browser. The on-screen preview, the downloaded SVG or PDF and the printed page all come from that one run, so nothing is laid out twice. The same template and data give the same bytes, because the pages come from one deterministic module, not from each browser's layout and print path; printing HTML and CSS varies in page breaks, fonts, margins and the print dialog. pscat's tests check that the WebAssembly build's SVG and PDF are byte-identical to the command-line tool's and repeat exactly (macOS on Apple silicon, and Linux in CI), and text is drawn as outlines, so the viewer's fonts do not matter. There is no server, account, GPU or AI model, and nothing is sampled.

What is released: SVG and PDF from the WebAssembly build are on main since #1003 (2026-11-04), not in 0.7.0-rc.3 or any earlier release, which give a web page RGBA pixels only. The JavaScript page has the API.

print-shop is an example of what can be built on pscat: menus from CSV in three PostScript templates, and a two-sided business card with bleed, laid out by PostScript and rendered in the browser to SVG and PDF. Its tests show byte-identical SVG, PDF and layout logs on repeat runs, and 1-, 40- and 500-item menus that place every item once within the measured columns. Its verification record has headless Chrome 156 passing its checks served and as one offline HTML file (desktop, and mobile emulation), and a PDF downloaded in Chrome byte-identical to the Node-rendered one. Its PDFs are RGB, with no PDF/X, TrimBox, BleedBox or crop marks. It pins a pre-release pscat (a 0.6.3 branch plus the patch that became the SVG and PDF output on main) until print-shop#16 repins it.

Many documents: write the template once, render each one

For thousands of menus, cards, labels, certificates or personalized letters, an image-model or LLM call per document means, as of November 2026, a per-image or per-token price and its latency, rate limits or a GPU, an API dependency, output that differs each time and needs checking, and the wrong words or numbers described above. With pscat an LLM can help write the template once; after that each document is a deterministic CPU render, data in and pages out, on a laptop, a server or the user's browser.

Measured on print-shop's own jobs (Apple M4 Mac mini, 16 GB, macOS 15.7, 2026-11-04, one process at a time, medians of 20): a two-sided business card in about 9 ms, a 32-page, 500-item menu to PDF in about 1.9 s with native pscat, and 1000 personalized cards one after another in about 9 s. The full table, including the WebAssembly build, is in the guide. These measure pscat only; we quote no figures for image models or LLMs.

pscat's weak spots

Not photorealistic. Its painterly look is recognisably its own. Someone, you or an agent, has to write the program, and a detailed painting takes several render-look-refine rounds. No 1D barcodes yet, and text only in the scripts its fonts cover.

Combining them

The image model paints the atmosphere; pscat sets the type, QR code, formula or chart on top and writes the print-ready PDF. pscat with an image model has two worked hybrid examples, each compared with the image model alone and pscat alone, with the facts checked.
